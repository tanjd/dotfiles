# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Overview

Personal dotfiles for WSL (Ubuntu) and macOS. Plain shell scripts and config files that get symlinked into `$HOME` (and, for one file, into the Windows side of a WSL2 machine). See README.md for the full file-to-symlink mapping.

## Install commands

- `./install.sh` — shared/cross-platform install, run automatically by devcontainers. First installs zsh itself via `apt-get`/`brew` if the `zsh` binary isn't found (the oh-my-zsh installer hard-exits with "Zsh is not installed" otherwise — bare Ubuntu, including GitHub Actions' `ubuntu-latest` runner, doesn't ship it by default). Then installs oh-my-zsh itself (unattended — no prompt, no shell launch, no `chsh`) if `~/.oh-my-zsh` doesn't exist, **before** the `.zshrc` symlink step — the oh-my-zsh installer overwrites `~/.zshrc` with its own template unless it runs first and gets overwritten by our symlink, not the other way around. Then symlinks `.zshrc`, `.gitignore_global`, `.claude/settings.json`, and each skill listed in `INSTALLED_SKILLS` individually (not the whole `.claude/skills/` directory — see below), and installs the oh-my-zsh custom plugins (`zsh-autosuggestions`, `zsh-syntax-highlighting`) into `$ZSH_CUSTOM/plugins` via the shared `clone_or_update` helper in `install-lib.sh` — a `--depth=1` clone when absent, otherwise a shallow `fetch` + `reset --hard` onto upstream HEAD. Re-running deliberately *updates* them rather than skipping: oh-my-zsh's `zstyle ':omz:update' mode auto` only updates oh-my-zsh core and leaves `$ZSH_CUSTOM` alone, so an if-missing check would freeze each plugin at whatever commit was HEAD on install day. (`fetch`+`reset` rather than `git pull` because merging into a `--depth=1` grafted history fails with "unrelated histories".) The update leg is deliberately **best-effort** — an unreachable remote warns and keeps the existing checkout instead of failing, because `install.sh` runs under `set -e` and an existing clone used to mean zero network calls, so a hard failure would abort an offline re-run before the Claude Code symlink steps that come after it. The initial clone stays fatal (there's nothing usable to fall back to). Tradeoff: the plugins now track upstream `master`, so a bad upstream commit can reach a devcontainer on rebuild — pin to release tags if that ever bites.
- `./install.wsl.sh` — WSL-only, run manually once per new WSL2 environment. Calls `install.sh` first, then additionally symlinks `gitconfig.wsl` → `~/.gitconfig`, `.config/git/allowed_signers` → `~/.config/git/allowed_signers`, and `ssh_config.wsl` → `~/.ssh/config`. Also symlinks `windows-terminal-settings.json` onto the Windows side via `/mnt/c/Users/tanjd/AppData/Local/Packages/Microsoft.WindowsTerminal_8wekyb3d8bbwe/LocalState/settings.json`, guarded behind an actual WSL detection check (`grep -qi microsoft /proc/version`) plus a path-exists check — so this step no-ops safely in CI or on a machine where that package hash differs, rather than assuming "this script is named `.wsl.sh` so it's always real WSL." This last link does *not* use `link_file`: a plain WSL `ln -s` stores a Linux path as the target, which Windows Terminal (a native Windows process) can't resolve — it fails with "the file cannot be accessed by the system." Instead the script shells out to `powershell.exe` to create a Windows-native symlink targeting the `\\wsl.localhost\...` UNC form of the file, which requires Developer Mode enabled (or an elevated shell) — the step warns and no-ops rather than aborting the script if that's missing.
- The other three WSL links, and both scripts' cross-platform links, use the shared `link_file` helper in `install-lib.sh`, which backs up any pre-existing non-symlink file at the target path to `<path>.bak` before symlinking — so a forgotten pre-existing `.zshrc`/`.gitconfig` on a machine is never silently clobbered. Re-running is idempotent: once a path is our symlink, subsequent runs skip the backup step.
- `./install.macos.sh [personal|work]` — macOS only, run manually once per new Mac. Calls `install.sh` first, then symlinks `gitconfig.macos-<arg>` (default `personal`) → `~/.gitconfig`, `.config/git/allowed_signers` → `~/.config/git/allowed_signers`, and `ssh_config.macos` → `~/.ssh/config`. Mirrors `install.wsl.sh`'s structure exactly (minus the Windows Terminal step, which has no macOS equivalent).
- `./install.macos-dev.sh [personal|work]` — macOS only, run manually once per new Mac, separate from `install.macos.sh` since it's optional package installation rather than baseline symlinking. Runs `brew bundle --file=Brewfile.macos-dev`, then symlinks `colima.yaml.macos-<arg>` (default `personal`) → `~/.colima/_templates/default.yaml` via the shared `link_file` helper.
- `./install.macos-personal.sh` — macOS only, run manually once per new Mac. Runs `brew bundle --file=Brewfile.macos-personal`. No symlinking.
- `Brewfile` (repo root) lists cross-platform Homebrew/Linuxbrew formulae and casks (`gcc`, `gh`, `node`, `rtk`, `jq`, `tree`, `claude-code` cask). Not symlinked or run automatically by any install script — apply manually with `brew bundle --file=Brewfile`. Deliberately excludes winget entries and npm globals that `brew bundle dump` also picks up on this machine — those aren't portable to macOS and aren't Homebrew's concern.
- `Brewfile.macos-dev` (font-jetbrains-mono, visual-studio-code, colima, docker, docker-compose, zsh-autocomplete) and `Brewfile.macos-personal` (obsidian, tailscale) are separate macOS-only Brewfiles, split by purpose rather than an `if OS.mac? ... end` block inside the shared `Brewfile` — this lets a machine install dev tooling without personal apps (or vice versa), and each stays its own small Ruby DSL file evaluated by `brew bundle`. 1Password is deliberately absent from every Brewfile: it's needed for SSH auth before any of this tooling can even be pulled down, so it's a manual/MDM-installed prerequisite rather than something these scripts bootstrap.
- `.github/workflows/test-install.yml` runs `install.sh` on Ubuntu + macOS runners, `install.wsl.sh` on Ubuntu, and `install.macos.sh`/`install.macos-dev.sh`/`install.macos-personal.sh` on macOS, on every push/PR — the only CI in this repo, exists purely to catch a broken install script before it hits a real machine.

There is no build, lint, or test tooling beyond that CI workflow (no Makefile, no package.json).

## Architecture

- **Platform split happens at install time**, via separate scripts/files rather than in-script branching: `install.sh` (shared baseline) vs `install.wsl.sh`/`install.macos.sh` (platform supersets) vs `gitconfig.wsl`/`ssh_config.wsl` and `gitconfig.macos-*`/`ssh_config.macos` (platform-specific configs, `.wsl`/`.macos` suffix convention — their contents are genuinely platform-specific, e.g. each `ssh_config.*`'s `IdentityAgent` points at a different 1Password agent socket path per platform). `gitconfig.macos-*` is further split by machine *role* (`-personal`/`-work`, like `colima.yaml.macos-*`) rather than platform, since both run on the same macOS platform but need different identities — see the git-identity-switching bullet below.
- **Two runtime OS-detection conditionals** exist in `.zshrc`: `grep -qi microsoft /proc/version` for WSL (sets Linuxbrew PATH and `ssh`/`ssh-add` aliases pointed at the Windows `.exe` binaries for SSH agent interop), and `uname == Darwin` for macOS (evals `brew shellenv` from either the Apple Silicon or Intel Homebrew prefix, exports `SSH_AUTH_SOCK` for the 1Password SSH agent, and — guarded behind its own `[[ -f ... ]]` check, since it's optional tooling installed separately via `install.macos-dev.sh` — wires up `zsh-autocomplete` in place of oh-my-zsh's default `compinit`). The `zsh-autocomplete` setup sets `ZSH_AUTOCOMPLETE_LOADED` so the two later Darwin-only blocks (matcher-list save/restore around `oh-my-zsh.sh`, and post-load keybinding fixes) only run when the plugin actually loaded, not on every Mac.
- This repo doubles as the source of truth for the user's own Claude Code global config: `.claude/settings.json` here is symlinked to `~/.claude/settings.json`, and skills under `.claude/skills/` are symlinked individually per `INSTALLED_SKILLS` in `install.sh` (currently just `commit`). Editing them changes the user's actual Claude Code setup on any machine where the install scripts have run.
- `.claude/skills/create-pr/` is intentionally **not** installed globally — it's kept here for reference only. Repos that need PR-creation automation (e.g. `core-repository`) define their own local `.claude/skills/create-pr/` override with repo-specific conventions, which always takes precedence over any global skill regardless of whether the global one is installed.
- Git commit signing uses SSH keys (not GPG): `gitconfig.wsl`/`gitconfig.macos-*` all set `gpg.format = ssh` and sign via their platform's 1Password SSH-signing binary (WSL bridge `.exe` vs. macOS's native `op-ssh-sign` inside `1Password.app`); `.config/git/allowed_signers` is shared cross-platform and holds the public key used to verify signatures. `gitconfig.macos-*` uses `~` expansion for `allowedSignersFile` (matching `core.excludesfile`'s existing pattern) rather than a hardcoded path, since the WSL and macOS home directories use different usernames (`tanjd` vs. `jeddytan`).
- `colima.yaml.macos-personal`/`colima.yaml.macos-work` are Colima config *templates* (macOS only, one symlinked by `install.macos-dev.sh [personal|work]`) at `~/.colima/_templates/default.yaml`. Split by machine rather than a single file, since the work laptop runs meaningfully bigger VM specs — unlike the git-identity split, this isn't something a runtime check can key off (it's a whole-machine choice made once, not a per-repo one), so it's a manual argument to the install script instead. Both are the full commented template `colima template` generates (every field documented with its default), so the diff between the two files *is* the documentation of what's actually customized: `cpu`/`memory`/`disk` (4/4/100 personal vs. 6/16/150 work), `arch: aarch64` + `vmType: vz` + `mountType: virtiofs` + `rosetta: true` (both, Apple Silicon's fast path instead of the QEMU/sshfs defaults), and `forwardAgent: true` (work only, forwards the host's 1Password SSH agent into the VM). The template is only applied when a Colima profile is first created (config precedence: defaults → template → profile → CLI flags), so it must be in place before the first `colima start`; overwriting it later doesn't affect an already-created VM.
- `ssh_config.macos` declares `Include ~/.colima/ssh_config` itself, rather than leaving Colima to inject that line on first `colima start` — since `ssh_config.macos` is symlinked straight onto `~/.ssh/config`, a Colima-injected line would otherwise get written through the symlink into this tracked repo file. A missing `Include` target is silently ignored by `ssh`, so this is safe before Colima ever creates that file.
- **Work-laptop git identity switching**: `gitconfig.macos-work` is `gitconfig.macos-personal` plus two `includeIf "hasconfig:remote.*.url:..."` blocks (git ≥2.36) that match Autodesk remotes in both URL forms (`https://git.autodesk.com/**` and the SSH-rewritten `git@git.autodesk.com:**`) and load `~/.gitconfig-work` instead of the personal `[user]` — needed because personal + work repos both live under `~/projects/` with no folder-level separation, so the switch has to key off the remote rather than the path. `~/.gitconfig-work` itself is intentionally untracked — hand-created once on the work laptop with the Autodesk identity plus the `git@git.autodesk.com:` insteadOf rewrite — since employer email/signing key shouldn't be committed to a personal dotfiles repo. `gitconfig.macos-personal` has none of this: a personal Mac never has an Autodesk remote to match, so there's nothing to gain from carrying the includeIf blocks there too.
